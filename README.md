# BidRadar

给广告出价算法工程师看的研究简报。把公开论文、技术文章和代码更新整理成几分钟能读完的内容，发到个人飞书群。

重点回答四个问题：**解决什么问题、方法改在哪里、结果可信到哪一步、读者能借鉴什么。** 每篇最多100个可见字符，默认最多20篇；资料不足时少发，评分依据和引文留在本机。

## 简报长什么样

下面是排版示例，内容为虚构测试案例，不代表真实研究或实验结果。

> **重点阅读**
>
> **1. 冷启动出价｜新研究**
>
> 用条件扩散补充稀缺轨迹。同预算离线测试成本下降，尚无线上验证。
>
> 借鉴数据不足时的轨迹生成。
>
> 含金量8/10 · 相关性9/10
>
> **公司动态**
>
> 阿里妈妈：本期未取得可核查资料。
>
> 美团：有相关资料，本期未推荐。

真实简报的标题可点击查看来源。开头是有证据支持的本期看点，随后依次为重点阅读、值得跟进、旧文补读和公司动态；没有内容的栏目不显示。候选取舍、评分分项、原文短引文和采集日志另存，不挤进阅读正文。

### 固定的编辑标准

| 读者需要作出的判断 | 一条合格推荐必须提供什么 |
|---|---|
| 这是不是我的问题 | 标题或首句点出冷启动、预算、价值估计、反馈或风险等具体问题 |
| 方法有什么变化 | 一项具体机制，说明改在何处；避免只说“用了Agent/大模型” |
| 结果能信到哪一步 | 结果紧贴线上/离线范围、比较条件或证据缺口；未公开幅度时保留定性结果 |
| 我为什么要打开原文 | 一句具体阅读用途，例如借鉴探索机制、压力评测或故障恢复；与实验效果分开 |
| 现在该读哪几篇 | 本期变化在前，旧文在后；证据不足列入跟进，重复与泛相关内容暂缓 |

每条按“标题与更新性质 → 方法、成果与边界 → 阅读用途 → 两项评分”组织。100字内优先保留关键条件，删除宣传语和次要数字；完整评分理由在本机依据中查看。

本期看点只提炼至少两项独立研究之间的互补、差异或共同问题；资料不足时留空，不拼出行业共识。公司动态分别说明可核查发现和采集空缺，跨公司判断需要多家公司的一手依据。

表达方式参考了 [Nature的研究简报](https://media.nature.com/original/magazine-assets/d41586-024-02935-z/d41586-024-02935-z.pdf) 对问题、方法及限制的组织，以及 [Google Research的在线分配研究文章](https://research.google/blog/robust-online-allocation-with-dual-mirror-descent/) 对预算困境、机制和验证范围的说明。这些范例用于制定编辑标准，自动推荐质量仍需持续人工评估。

## 怎么筛选

```text
公开论文 / 技术文章 / 仓库更新
          ↓
时间核验 → 去重 → 出价主题筛选
          ↓
AI提炼 → 引文与评分检查 → 独立上下文复审
          ↓
本地预览 → 飞书简报
```

- **先看相关性。** 关注生成式出价、预算约束、反馈建模和广告Agent。公司名或热门术语本身不加分。
- **数字要有条件。** 区分线上与离线、相对提升与百分点、成本增长与广告主收益。口径说不清时保留定性结果，或暂不推荐。
- **证据不足就写“待评”。** 仅拿到摘要或README，不等于原研究质量差。此类资料最多列入2篇“值得跟进”，明确阅读范围和限制。
- **每条结论可追溯。** 技术和结果须有同一研究的原文短引文。公司归属按来源核验，关键词检索不等于公司官方发布；转载也不算第二份独立证据。
- **复审具体成稿。** 独立上下文检查摘要、数字、归因和新旧判断；最多修订一次并重新复审。未通过的技术内容不会推送。

### 评分怎么看

| 评分 | 组成 | 用途 |
|---|---|---|
| 含金量，满分10分 | 技术增量0–3、证据0–4、工业价值0–3 | 判断是否值得深入阅读 |
| 相关性，满分10分 | 出价业务0–5、技术契合0–3、可迁移性0–2 | 判断与日常工作有多近 |

主推荐两项均须达到7分。相关性至少7分但证据不足的，可以作为观察，含金量标为“待评”。评分是阅读判断，尚未通过真实案例完成人工标定，不是效果认证。

## 信息来源

配置覆盖arXiv、团队技术博客、公开仓库、智源社区和行业媒体。具体入口见 [config.example.toml](config.example.toml)。

| 来源 | 主要作用 | 阅读时的边界 |
|---|---|---|
| arXiv | 发现出价、转化与延迟反馈论文 | 按关键词召回；摘要不能代替全文 |
| 团队技术博客 | 了解工业方法和落地细节 | 订阅条目有限，不保证历史完整 |
| 公开仓库 | 跟进实现与代码变化 | README、诊断模式和正式评测要分清 |
| 智源社区 | 发现技术文章和公开同步内容 | 社区分享时间不一定是原文首发；平台署名不是独立身份认证 |
| InfoQ、量子位 | 补充发现行业文章 | 报道、宣传和转载不能替代原始实验 |

来源出错会单独显示，不能据此判断某家公司没有新成果。公司动态只总结已取得的可核查资料；跨研究观察不比较不同任务的涨幅，也不强行概括行业共识。

## 快速开始

需要 **Python 3.11+、curl、已登录的Codex CLI**。只使用Python标准库，无需安装Python依赖。定时任务目前支持macOS。

先用 `python3 --version` 确认版本。若系统默认版本较旧，以下命令中的 `python3` 请换成已安装的 `python3.12` 等版本。

```sh
python3 bidradar.py init
```

在 `~/.config/bidradar/config.toml` 中填写个人飞书群自定义机器人的Webhook和签名密钥，文件权限须为600。机器人开启签名校验。凭证放在代码目录之外。

```sh
python3 bidradar.py collect       # 只采集，不调用AI
python3 bidradar.py brief         # 提炼并复审，保存预览
python3 bidradar.py quality       # 检查当前成稿，不调用AI
python3 bidradar.py digest        # 重新打开当前预览，不调用AI
```

预览位于 `~/Library/Application Support/BidRadar/digests/`。原文依据和取舍记录在同级的 `reviews/` 中。新输入尚未通过复审时，预览只显示状态。

### 接入飞书与定时运行

```sh
python3 bidradar.py notify-check      # 发送一次连接确认
python3 bidradar.py digest --send     # 手动发送已通过复审的简报
python3 bidradar.py install-schedule  # 注册macOS定时任务
```

每天早上09:00检查周期，并缓存InfoQ和量子位的短RSS；**每15天集中采集、审阅、推送一次**。AI处理完成后送达，不保证整点送达。睡眠、关机和断网可能造成延迟；锁屏时电脑保持唤醒即可运行。程序不修改电源设置。

条数在 `[brief].max_items` 中配置，默认20；推荐和观察合计计数。标题、编号、标点和评分均计入每条100字符，链接地址不计。消息正文最多2,000字符，超限时整篇减少，不截断结论或限制条件。

更多命令、调用预算和故障处理见 [运行说明](docs/operations.md)。

## 隐私与可靠性

- 配置、SQLite数据库、个人备注和运行日志保存在用户目录，均不属于公开源码。个人备注不发送给模型或飞书。
- 模型接收选定公开资料、公开投递历史摘要和本机阅读标签，个人备注不发送。CLI使用独立临时目录，禁用工具、插件和MCP配置；审阅期间检测到工具调用就拒绝结果。
- 采集使用HTTPS和明确的主机白名单，不绕过登录、验证码或付费限制。来源文本按不可信输入处理。
- 调用预算持久化，失败也计数；重启不会刷新预算。正常每日和自动周期各最多6次调用。
- 推送前记录待发内容，收到飞书成功响应后才记为已发送。结果不确定时停止自动重发，需要人工核对群记录。

## 当前边界

这是个人研究情报工具，发现延迟通常为0–15天，加上源站索引延迟。尚未实现论文PDF全文解析、完整语义去重、自动复现或全渠道覆盖，也没有量化推荐准确率和漏报率。程序校验和模型复审都可能漏错，关键研究仍需阅读原文。
